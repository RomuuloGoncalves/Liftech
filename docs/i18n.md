# Internacionalização (i18n)

Este documento descreve como o suporte a múltiplos idiomas funciona no frontend da Liftech: o que foi instalado, onde cada peça vive e como tudo se conecta em tempo de execução.

---

## Bibliotecas

| Biblioteca | Versão | Para que serve |
|---|---|---|
| `i18next` | ^23 | Motor de tradução, responsável por carregar recursos e resolver chaves |
| `react-i18next` | ^14 | Adaptador React: fornece `useTranslation` e `Trans` para os componentes |

---

| Código | Idioma |

| `pt-BR` | Português (Brasil) — padrão e fallback |

## Inicialização

O arquivo `src/config/i18n.ts` é importado em `main.tsx` antes do `ReactDOM.createRoot`. Isso garante que o i18next esteja pronto antes do React montar qualquer componente.

```ts
// main.tsx
import './config/i18n'
import ReactDOM from 'react-dom/client'
// ...
```

Dentro de `i18n.ts`, a inicialização é síncrona (`initImmediate: false`). Não há `<Suspense>` nem estado de carregamento: quando o app abre, os textos já estão disponíveis.

### Escolha do idioma inicial

```
1. Lê localStorage['liftech-lang']
2. Valida se o valor está em VALID_LANGUAGES
3. Se válido → usa esse idioma
4. Se ausente ou inválido → usa 'pt-BR'
```

### Recursos inline

Todos os arquivos JSON são importados estaticamente no `i18n.ts` e registrados em memória. Não há requisição de rede para buscar traduções.

```ts
resources: {
  'pt-BR': { translation: ptBR },
  'en-US': { translation: enUS },
  // ...
}
```

## Estrutura das chaves de tradução

Cada arquivo JSON tem, entre outros, estes módulos:

| Módulo | Conteúdo |
|---|---|
| `common` | Ações genéricas: Cancelar, Salvar, Fechar, Cadastrar |
| `navigation` | Nomes de rotas, labels do menu lateral, textos do rodapé |
| `machines` | Tudo relacionado a máquinas: status, campos de formulário, estados vazios |
| `alerts` | Tela Histórico de Alertas: selo Acidentes, busca, estado vazio e níveis de urgência (`urgency.media/alta/critica`) |
| `languages` | Nomes dos idiomas exibidos no seletor do Header |

### Exemplo de uso nos componentes

```tsx
import { useTranslation } from 'react-i18next'

const { t } = useTranslation()

<button>{t('machines.registerButton')}</button>
// pt-BR → "Cadastrar Máquina"
// en-US → "Register Machine"
```

## Hook `useLanguage`

O `useLanguage` concentra a lógica de troca de idioma. Componentes que só precisam exibir texto em tradução usam `useTranslation` diretamente; o `useLanguage` é para quem precisa da lista de idiomas ou de trocar o idioma ativo (hoje só o `Header`).

```ts
const { language, changeLanguage, languages } = useLanguage()
```

| Campo | Tipo | Descrição |
|---|---|---|
| `language` | `string` | Código do idioma ativo (ex.: `'en-US'`) |
| `changeLanguage` | `(code: string) => void` | Troca o idioma; ignora silenciosamente códigos inválidos |
| `languages` | `LanguageOption[]` | Lista dos 7 idiomas com `code`, `nativeLabel`, `flag` |

Ao chamar `changeLanguage('en-US')`, duas coisas acontecem: o i18next atualiza o idioma ativo e o React re-renderiza todos os componentes com `useTranslation`. O `localStorage['liftech-lang']` é gravado para que a escolha persista na próxima sessão.

Códigos fora de `VALID_LANGUAGES` são ignorados sem lançar exceção.

---

## Fallback

Se uma chave existir em `pt-BR` mas não no idioma ativo, o i18next retorna o valor em `pt-BR`. Se a chave não existir em nenhum recurso, o i18next retorna a própria chave como string (ex.: `'navigation.overview'`). Esse comportamento serve de aviso visível durante desenvolvimento, mas nunca acontece em produção se todos os arquivos JSON estiverem em sincronia.

## Adicionando um novo idioma

1. Crie `src/locales/<código>/translation.json` com todos os módulos (`common`, `navigation`, `machines`, `languages`).
2. Importe e registre o JSON em `src/config/i18n.ts`.
3. Adicione o código em `VALID_LANGUAGES` em `src/types/i18n.ts`.
4. Adicione a entrada correspondente no array de `LanguageOption` dentro de `useLanguage.ts`.

Os testes de estrutura em `src/test/config/i18n.test.ts` vão falhar imediatamente se o novo locale estiver faltando algum módulo ou chave obrigatória do `navigation`.

---

## Adicionando uma nova chave de tradução

1. Adicione a chave em `pt-BR/translation.json` dentro do módulo adequado.
2. Adicione a mesma chave nos outros 6 arquivos de tradução.
3. Use `t('modulo.chave')` no componente.

O teste `'navigation module in every locale contains pages, feedback, privacy keys'` em `i18n.test.ts` cobre os campos críticos do módulo `navigation`. Para módulos novos ou campos novos em outros módulos, adicione um caso análogo.

## Decisões de arquitetura

Estas decisões estão registradas como AD-006 em `.specs/STATE.md`.

**Recursos inline, sem lazy-load.** Os JSON são importados no bundle. Para o volume atual de textos (menos de 2 KB por locale), o custo de carregamento é irrelevante e elimina a necessidade de `<Suspense>`.

**Idioma padrão fixo em `pt-BR`.** O app não detecta o idioma do browser. A razão é que o produto é voltado a um contexto onde o idioma padrão é conhecido; detecção automática adicionaria complexidade sem benefício claro para os usuários atuais.

**`i18next-browser-languagedetector` não instalado.** Consequência direta da decisão acima.

**Namespace único `translation`.** Um namespace por feature traria isolamento, mas também exigiria que cada `useTranslation('meuNamespace')` e cada arquivo de recurso fossem gerenciados separadamente. Com quatro módulos dentro de um único `translation`, a organização é suficiente e o overhead é zero.
